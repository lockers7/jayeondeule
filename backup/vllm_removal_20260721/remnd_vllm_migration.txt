# vLLM 마이그레이션 가이드 (2026-05-25)

> **[2026-07-04 현행 상태]** LLM_BACKEND=ollama(기본) 유지, vllm.service 비활성.
> 동시성 문제는 이후 앱 레벨 5중 조율로 해결됨: `OLLAMA_NUM_PARALLEL=1`(의도적 직렬화) +
> llm_call_lock(fcntl 물리 락) + busy 마커 양보 + 제어 중재(arbitration) + 채팅 우선순위 게이트.
> 즉 "우선순위 있는 직렬 처리"가 현행 설계라 vLLM 전환의 긴급성은 낮음 — 본 가이드는
> 향후 동시 처리량이 실제로 필요해질 때의 업그레이드 절차로 유지한다.
> 주의: 전환 시 아래 5중 조율(특히 NUM_PARALLEL=1 전제의 우선순위 설계)과의 정합 재설계 필요.

Ollama 가 production 동시 요청 한계 (당시 `OLLAMA_NUM_PARALLEL=2`) 로 ANALYZER 503 fallback 의존 상태에 빠진 사고 (2026-05-25 19:42 / 20:38) 를 계기로 vLLM 전환 옵션을 코드 레벨로 준비했다. **default 는 Ollama 그대로 유지** — 본 문서는 vLLM 활성화 절차와 rollback 만 다룬다.

## 0. 핵심 원칙

- **추상화 레이어** 만 추가됨. 코드는 환경변수 `LLM_BACKEND` 로 분기.
- default `LLM_BACKEND=ollama` (미설정 시 동작) — 기존 동작 100% 보전.
- vLLM 실패 시 Ollama 로 자동 폴백 (안전망, `llm_transport._ollama_chat`).
- **embedder.py 는 항상 Ollama 사용** — vLLM 임베딩 지원이 제한적이라 분리.

## 3. 리스크 + 완화책

| 리스크 | 영향 | 완화 |
|---|---|---|
| **VRAM 한계** (RTX 5060 Ti 16GB) | gemma3:27b AWQ-INT4 ≈ 18GB. GPU0+1 분산 필요할 수도. | `VLLM_TENSOR_PARALLEL=2` 로 2장 GPU 분산. 또는 더 작은 모델 (gemma3:12b) 검토. |
| **모델 로드 60~180초** | 첫 활성화 시 응답 지연 | systemd `TimeoutStartSec=300`. `--enable-prefix-caching` 옵션 검토. |
| **Tool calling 동작 차이** | LLM 이 도구 못 부를 위험 | `tool_choice="auto"` 적용됨. 회귀 테스트 필수. |
| **format=schema 호환** | JSON 강제 정확도 차이 | OpenAI `response_format={"type":"json_schema", strict:true}` 매핑. ai_control 환경제어 가장 시급 검증 대상. |
| **임베딩 미지원** | embedder 깨질 가능성 | 의도적으로 Ollama 그대로. 영구 분리. |

## 4. Rollback

```bash
# .env 에서 LLM_BACKEND 줄 제거 (또는 ollama 로 변경)
sed -i '/^LLM_BACKEND=vllm/d' /workspace/jayeondeule/.env

# vLLM 서버 중지 (선택 — 동시 실행도 무관)
sudo systemctl stop vllm.service

# APP 재시작 — 다시 Ollama 사용
sudo /workspace/jayeondeule/agriAiCore restart 00
```

# [2026-07-05 추가 분석] 신형 서빙 엔진(vLLM/SGLang) 전환 타당성 — HW 실측 기반

## 실측 프로파일 (2026-07-05)
- GPU: RTX 5060 Ti 16GB(CC 12.0) + GTX 1660 SUPER 6GB(CC 7.5, GTX급 — 텐서코어 없음)
- gemma3:27b Q4_K_M(17.4GB)은 **단일 16GB 에 미탑재** → 현재 llama.cpp 이기종 레이어 분산
  (5060Ti 13.0GB + 1660S 4.7GB)으로만 27B 구동 중.
- 지연 실측: 1단계 분석 평균 80s(65~162), 3단계 답변 평균 84s(10~204), 전체 호출 평균 75s(n=53).
  주원인은 생성속도가 아니라 **prefill 재계산** — 제어/agent/채팅 3주체가 서로 다른 대형
  프리픽스로 교대 호출 → NUM_PARALLEL=1 단일 슬롯 KV 캐시가 매번 파기.

## 현 HW 판정: 전환 불가 (27B 유지 전제)
- vLLM/SGLang 은 **이기종 GPU 텐서병렬 미지원** — 사실상 5060 Ti 16GB 단독만 사용 가능.
  (기존 §3 "VLLM_TENSOR_PARALLEL=2 로 2장 분산" 완화책은 실현 불가로 정정 —
   1660 SUPER 는 CC 7.5 + 6GB 라 TP 참여 불가, AWQ marlin/FP8 커널은 sm80+ 요구)
- gemma3-27b 4bit(AWQ/GPTQ) 가중치 ≈ 15.5~16.5GB → 16GB 에 KV 캐시 공간 없음 → 27B 불가.
- 12B 급 다운그레이드 시 탑재는 가능하나 품질 후퇴(도구선택 신뢰도가 이미 병목) — 부적합.
- 결론: **현 구성에서 Ollama(llama.cpp) 가 27B 를 돌리는 유일한 경로. 전환 보류가 정답.**

## GPU 업그레이드 후 로드맵 (전환의 실익이 생기는 시점)
- 기준: 단일 24GB(4090급) → 27B AWQ-INT4 + KV 여유 / 단일 32GB(5090급) → FP8 까지 가능.
- **1순위 SGLang**: RadixAttention 프리픽스 트리 캐시가 "3주체 × 대형 고정 프리픽스 교대 호출"
  패턴에 정확히 부합 — 주체별 프리픽스가 캐시에 병존, 매 호출 prefill 수십 배 절감.
  xgrammar 구조화 출력(format=schema 대체) 지원. OpenAI 호환 API.
- 2순위 vLLM: APC(자동 프리픽스 캐시) + guided JSON — 성숙도·문서화 강점. 기존 준비물
  (LLM_BACKEND 스위치, vllm.service, 테스트 22종) 재사용.
- 정량 기대(보수적): 분석 80s → 5~15s(프리픽스 적중 시), 생성 tok/s 2~4배,
  채팅 체감 100~250s → 20~40s, 제어 사이클 LLM 판단 30~60s → 5~15s.
- 전환 표면: llm_transport OpenAI 호환 어댑터(SGLang/vLLM 공용 가능) + json_schema 매핑 검증.
  임베딩(bge-m3)은 기존 설계대로 Ollama 영구 잔류. 5중 동시성 조율은 앱 레벨이라 그대로 유지.
- 검증 절차: 병행 구동(포트 분리) → 동일 질의셋 회귀(도구선택/JSON 스키마/제어결정 A/B 일치율)
  → 카나리 전환 → 실패 시 §4 롤백.

## 현 HW 에서의 소폭 개선 여지 (선택, 소스 변경 없음)
- OLLAMA_FLASH_ATTENTION=1 + OLLAMA_KV_CACHE_TYPE=q8_0 시험 — KV 메모리 절반+prefill 개선
  가능성. 단 1660 SUPER(sm75, 텐서코어 없음) 호환이 관건이라 반드시 시험 후 적용.
- (참고) qwen3:30b-a3b(MoE, 활성 3.3B — 디스크 보유)는 동일 HW 에서 디코드가 수 배 빠르고
  tool-call 성향이 다름 — 도구선택 신뢰도 문제와 묶어 별도 A/B 가치는 있음(모델 축 변경이라 별건).
