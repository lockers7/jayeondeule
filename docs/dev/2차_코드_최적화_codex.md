- 대상: `agri_ai_core` 전체
- 목표: **기능/동작/응답 형식 변경 없이** 응답 지연(특히 p95) 최소화
- 제약: 릴레이/제어 안전 로직(지연 포함)은 성능보다 안전 우선, 동작 변경 금지

## 1) 분석 범위 및 방식 (2회 분석)

### 1-1. 1차 분석: 전체 코드 커버리지 점검
- `agri_ai_core` 하위 전체 파일을 전수 확인(58개 Python + 1개 CSS)
- API 진입점, LLM 오케스트레이션, RAG, DB, MCP, 제어 모듈까지 전 흐름 확인
- 요청 생애주기 기준으로 병목 후보 분류
  - 입력 수집/로깅
  - 컨텍스트 조회(DB+벡터)
  - RAG 검색/리랭킹
  - LLM 호출(본 답변 + 도구 호출 루프)
  - 후처리/응답 정리
  - 대화 저장

### 1-2. 2차 분석: 복잡도/핫스팟 중심 재점검
- 함수 복잡도 및 호출 빈도 관점으로 재분석
- 고복잡/핵심 함수 집중 확인

## 2) 핵심 결론

1. 현재 지연의 1순위는 LLM 추론/도구 루프 구간이다.
2. 다만 아래 항목은 기능 변경 없이도 줄일 수 있는 오버헤드다.
   - 과도한 동기식 상세 로깅(JSON pretty dump 포함)
   - RAG 다중 컬렉션 조회의 순차 처리
   - 임베딩/Chroma 재시도 대기(sleep) 누적
   - MCP 도구 호출 시 프로세스 생성/종료 비용
   - 후처리에서 조건부 추가 LLM 호출 가능성
3. 즉, "LLM이 느려서 어쩔 수 없음" 상태가 아니라,
   **LLM 시간은 유지하더라도 주변 파이프라인 최적화로 전체 지연(특히 p95) 개선 가능**하다.

## 3) 기능 훼손 없이 적용 가능한 최적화 항목

아래는 "응답 내용/기능 동일"을 유지하는 범위에서만 선정했다.

### A. 로깅 경량화 (무위험, 우선 적용)
- 대상
  - `src/ai/llm_client.py`
  - `src/ai/query_handler_simple.py`
  - `src/ai/tools_executor.py`
  - `api/app.py`
- 문제
  - 요청/응답 전체 JSON을 `indent=2`로 직렬화하여 INFO 레벨에 자주 기록
  - 핫패스에서 문자열 생성+I/O 비용 증가
- 조치
  - 기본 운영 레벨 `INFO` 유지 시, 대용량 payload는 요약 로그(길이/개수/상태코드/핵심 필드)로 축소
  - 상세 본문은 `DEBUG` 레벨에서만 출력
  - 샘플링 로깅(예: 1/N 요청) 옵션 추가
- 기대효과
  - CPU 사용량/GC 압박 감소
  - 짧은 질의에서 체감 지연 개선

### B. RAG 조회 병렬화 및 경량 캐시 (저위험)
- 대상
  - `src/ai/tools_executor.py` (`search_farm_knowledge`)
- 문제
  - 다중 컬렉션 조회가 순차 실행되어 I/O 대기 누적
- 조치
  - 동일 쿼리 벡터 기반 컬렉션 조회를 안전한 범위 내 병렬화
  - 동일 세션/단기 반복 질문의 임베딩 결과 TTL 캐시
- 기대효과
  - RAG 구간 대기시간 단축(특히 멀티컬렉션 환경)

### C. 후처리 파이프라인 조건 최적화 (중위험, 기능동등 검증 필요)
- 대상
  - `src/ai/llm_client.py` 최종 정리/존댓말 보정 구간
- 문제
  - 일부 케이스에서 "추가 LLM 보정 호출" 발생 가능
- 조치
  - 추가 호출이 필요한 조건을 더 엄격히 게이트
  - 규칙 기반 처리로 충분한 경우 재호출 금지
- 기대효과
  - 꼬리 지연(p95/p99) 감소
- 주의
  - 문체/출력 품질 회귀 테스트 필수

### D. MCP 호출 비용 절감 (중위험)
- 대상
  - `src/ai/mcp_client.py`
- 문제
  - 도구 호출마다 프로세스 생성/종료 비용이 발생할 수 있음
- 조치
  - 지속 연결(프로세스 재사용) 방식 도입 또는 연결 풀링
  - 타임아웃/에러 핸들링은 기존 정책 동일 유지
- 기대효과
  - 도구 연속 호출 시 누적 지연 감소

### E. 대화 저장 비동기 경계 재조정 (저~중위험)
- 대상
  - `src/ai/query_handler_simple.py`
- 문제
  - 일부 경로에서 응답 완료 전 동기 DB 저장이 체감 지연에 영향
- 조치
  - 사용자 응답 반환 이후 저장하도록 안전하게 후행 처리
  - 실패 시 재시도/로그 보강(내구성 유지)
- 기대효과
  - 사용자 체감 응답 시간 개선

### F. 재시도(backoff) 정책 미세조정 (저위험)
- 대상
  - `src/ai/rag/embedder.py`
  - `src/chroma/operations.py`
- 문제
  - 재시도 sleep 누적으로 tail latency 증가
- 조치
  - 실패 유형별 즉시실패/재시도 분리
  - 백오프 상한 조정, 전체 타임버짓 내에서만 재시도
- 기대효과
  - 장애 시 무의미한 대기 감소, 정상 시 영향 최소

## 4) 우선순위 및 실행 순서

## Phase 0. 기준선(Baseline) 측정
- 할 일
  - 단계별 타이머 계측 추가: `request -> context -> rag -> llm -> postprocess -> save`
  - 메트릭 수집: p50/p95/p99, TTFB, 완료시간, 토큰수, 도구호출횟수
- 산출물
  - 최적화 전 성능 리포트 1회

- 범위

## Phase 3. 중위험 개선
- 범위
  - C(후처리 추가 LLM 호출 게이트), D(MCP 프로세스 재사용)

  - 골든 질의셋 품질 비교 + 오류율/타임아웃 회귀 점검

## 5) 정량 목표 (기능동등 전제)

### 부록: 이번 분석의 최종 해석
- 현재 시스템은 이미 기능적으로 안정적이며, 대형 병목은 LLM 자체 추론 시간이다.
- 그러나 실제 사용자 체감 속도는 LLM 외부 구간(로깅/검색/후처리/저장) 최적화로도 분명히 개선 가능하다.
- 따라서 "LLM 속도 때문에 유지"를 기본으로 두되, **LLM 외 오버헤드를 줄이는 보수적 최적화**를 먼저 적용하는 것이 가장 안전하고 효과적이다.
