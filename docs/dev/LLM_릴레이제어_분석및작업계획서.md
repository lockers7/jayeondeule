## 1. 문제 현상

### 1차 대화 (11:10:44)
- **사용자 요청**: "제1재배사의 릴레이를 제어하고... 동작중인 릴레이는 중지, 중지된 릴레이는 동작시켜라"
- **LLM 동작**: `get_farm_realtime_data`로 릴레이 상태 **조회만** 수행 (tool_calls=1)
- **LLM 응답**: "중지하고, 동작시켰습니다"라고 답변하며 변경 전/후 표 출력
- **실제**: tool_calls=0 (반복2), 릴레이 **제어는 전혀 수행되지 않음**

### 2차 대화 (11:14:42)
- **사용자 요청**: "다시 이전 요구사항 수행하라"
- **LLM 동작**: tool_calls=0 (반복1), **도구를 아예 호출하지 않음**
- **LLM 응답**: 1차와 **동일한 표**를 그대로 출력 (변경전/후 동일)
- **실제**: 1차에서 제어가 안 됐으므로 DB 상태 변화 없음 → 다시 조회해도 같은 값

## 2. 근본 원인 분석

### 원인 A: 릴레이 제어 Tool 부재 (핵심 원인)
- 기존 tool 정의(tools_definition.py)에 `control_relay` 도구가 **존재하지 않음**
- LLM에게 제공된 tool 목록: `search_farm_knowledge`, `get_farm_realtime_data`, `search_web`, `fetch_url_content` (4개)
- 릴레이 상태를 **읽을 수는 있으나** (get_farm_realtime_data), **쓸 수는 없음**
- LLM이 "제어했다"는 응답은 **할루시네이션** (도구 없이 수행한 척)

### 원인 B: 시스템 프롬프트에 제어 규칙 부재
- 시스템 프롬프트에 "장치 제어 시 반드시 도구를 호출해야 한다"는 규칙 없음
- LLM이 제어 도구 없이도 "수행했다"고 답변하는 것을 제지할 장치 없음

### 원인 C: LLM의 릴레이-기능 매핑 오류
- DB에서 반환하는 데이터: `relay_1st_flag`, `relay_2st_flag`, ... (raw 키)
- LLM이 각 릴레이의 기능을 **잘못 추측**:
  - relay_1 → "조명" (실제: 물가열기)
  - relay_3 → "흡입팬" (실제: 배수밸브)
  - relay_5 → "습도 제어" (실제: 흡기팬)
  - relay_7 → "온도 제어" (실제: 조명)
- 원인: `get_farm_realtime_data`가 raw relay flag만 반환하고, 시멘틱 매핑 정보를 포함하지 않음

### 원인 D: 2차 대화에서 tool 미호출
- "다시 이전 요구사항 수행하라"라는 문맥적 참조 요청에 대해
- LLM이 이전 대화의 assistant 응답을 그대로 **복사/패러프레이즈**
- 현재 상태를 다시 조회하지 않고, 이전 응답 기반으로 답변 생성

### 원인 E: 수동제어 스케줄러의 덮어쓰기 가능성
- 로그에서 확인: `manual_control`이 10초 간격으로 환경제어 루프 실행 중
- LLM이 DB에 릴레이 값을 설정하더라도, `manual_control`이 즉시 덮어쓸 수 있음
- 11:10:44에 LLM 요청 → 11:10:45에 알고리즘 환경제어 실행 (1초 차이)
- 현재 재배사 1은 `알고리즘 수동제어` → `사용자 직접입력 모드` 전환 중

## 4. 추가 작업 계획

### 작업 1: 릴레이 조회 결과에 시멘틱 매핑 정보 포함
- **파일**: `agri_ai_core/src/ai/tools_executor.py` → `get_farm_realtime_data()`
- **문제**: 현재 relay 데이터가 `relay_1st_flag: true/false` 형태로만 반환됨
  - LLM이 relay_1이 어떤 장치인지 알 수 없어 "조명", "습도 제어" 등으로 잘못 추측
- **수정 방안**: relay 데이터 반환 시 시멘틱 매핑 정보를 함께 포함
  ```python
  # 현재: {"relay_1st_flag": false, ...}
  # 개선: {"relay_1st_flag": {"value": false, "name": "물가열기", "device": "water_heater_flag"}, ...}
  ```
- **참조**: `control_common.py`의 `reverse_pin_map()` + `SEMANTIC_LABELS` 활용
- **우선순위**: 높음 (LLM이 정확한 장치명을 알아야 올바른 제어 가능)

### 작업 2: 수동제어 스케줄러와의 충돌 방지
- **파일**: `agri_ai_core/src/control/manual_control.py`
- **문제**: 10초 간격 환경제어 루프가 LLM의 릴레이 설정을 즉시 덮어씀
- **수정 방안**:
  - 방안 A: LLM 제어 시 해당 재배사를 일시적으로 "사용자 직접입력 모드"로 전환
  - 방안 B: LLM 제어 후 일정 시간(예: 60초) 동안 해당 릴레이의 자동제어를 억제하는 "LLM 제어 잠금" 메커니즘
  - 방안 C: LLM 제어 결과를 `is_manual` 플래그로 연동하여 스케줄러가 해당 재배사를 "직접입력" 모드로 인식
- **참조**: 로그에서 `사용자 직접입력 모드` vs `알고리즘 수동제어` 분기 확인
- **우선순위**: 높음 (제어가 적용되더라도 즉시 덮어쓰여 무효화됨)

### 작업 3: 다중 릴레이 일괄 제어 지원
- **파일**: `tools_definition.py`, `tools_executor.py`
- **문제**: 현재 `control_relay`는 단일 장치만 제어 가능
  - "모든 릴레이 반전"과 같은 요청에는 16번의 tool call이 필요
  - Ollama의 tool call은 한 번에 1개씩 처리 → 16번 반복 = 매우 느림
- **수정 방안**:
  - `control_relay`에 `devices` 파라미터 추가 (복수 장치 일괄 제어)
  - 또는 `control_all_relays` 별도 tool 추가 (전체 릴레이 일괄 설정)
- **우선순위**: 중간 (단일 장치 제어는 이미 가능, 대량 제어 편의성)

### 작업 4: LLM 응답 검증 강화
- **파일**: `agri_ai_core/src/ai/llm_client.py`
- **문제**: LLM이 제어 요청을 받았으나 제어 tool을 호출하지 않고 답변만 생성
- **수정 방안**:
  - 사용자 요청에 "제어/켜/끄/중지/가동/작동" 키워드가 포함된 경우
  - 최종 답변 전에 `control_relay` tool이 호출되었는지 검증
  - 미호출 시 경고 로그 기록 또는 자동 재시도
- **우선순위**: 낮음 (시스템 프롬프트 규칙 8번으로 대부분 해결될 것으로 예상)

### 작업 5: 릴레이 기능명을 relay 조회 결과에 포함
- **파일**: `agri_ai_core/src/ai/tools_executor.py` → `get_farm_realtime_data()`
- **문제**: LLM이 relay_1st_flag가 무엇인지 모르고 추측함
- **수정 방안**: `data_type='relay'` 조회 시 각 relay flag에 한글 기능명 주석 추가
  ```json
  {
    "relay_1st_flag": false,
    "relay_mapping": {
      "relay_1st_flag": "물가열기",
      "relay_3st_flag": "배수밸브",
      "relay_5st_flag": "흡기팬",
      ...
    }
  }
  ```
- **참조**: `config/mappers.py`의 `RELAY_FIELD_MAPPING` 활용
- **우선순위**: 높음 (작업 1과 동일 목적, 구현 방식 선택)

## 6. 결론

### "제어가 안 된 것인가, LLM이 이해를 못한 것인가?"

**둘 다입니다.**

1. **제어 tool이 없었으므로** LLM이 제어를 수행할 **방법 자체가 없었습니다** (원인 A)
2. LLM은 제어 도구가 없는 상황에서 "수행했다"고 **거짓 답변**했습니다 (할루시네이션, 원인 A+B)
3. 2차 대화에서는 **도구를 아예 호출하지 않고** 이전 답변을 복사했습니다 (원인 D)
4. 릴레이-기능 매핑도 **잘못 추측**했습니다 (원인 C)
5. 설령 제어가 수행되더라도 **10초 후 스케줄러가 덮어씁니다** (원인 E)

이미 수정 완료된 작업(순위 1, 2)으로 핵심 원인(A, B)은 해결되었으며,
나머지 작업(순위 3~6)을 순차 적용하면 안정적인 LLM 릴레이 제어가 가능합니다.
